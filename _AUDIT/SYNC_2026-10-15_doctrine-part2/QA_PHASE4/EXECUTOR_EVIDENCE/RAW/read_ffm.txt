40: ## 1. What an FFM Is, In One Page
41: 
42: A **Frontend-First Module (FFM)** is a portable, self-contained folder dropped at `agent_docs/CURRENT_APP/<project>_<phase>_ffm/` inside a starter kit clone. It is the single source of truth that tells an AI coding tool (Claude Code, Codex CLI, Gemini CLI, etc.) **what to build, how to build it, and what not to touch.**
43: 
44: An FFM bundles:
45: 
46: - **Navigation** — entry-point files that route AI tools through the module
47: - **Doctrine** — the operating rules, forbidden zones, and conflict resolution order
48: - **Specification** — APP_BRIEF (scope), DATA_CONTRACT (data shapes), UI_SPEC (screens)
49: - **Methodology** — a frontend-first skill and a phase-by-phase playbook
50: - **Verification** — approval gates and a build checklist
51: - **Evidence** — design references and extraction artifacts (when applicable)

61: ## 2. The Factory Roles and Delivery Pattern
62: 
63: The FFM preparation stream retains Designer, Extractor, Architect and Engineer responsibilities. The complete delivery workflow also includes independent QA Executor and QA Lead responsibilities and the Director’s approval and release authority. Each role’s outputs feed the next role’s inputs; the preparation diagram below is not a complete release lifecycle.
64: 
65: ### The Roles
66: 
67: ```text
68: Current recon and approved brief / extraction evidence
69: → Architect authors DATA_CONTRACT before Design
70: → Designer authors UI_SPEC, tokens and the complete visual package
71: → Architect reconciles assembly, prepares module-specific QAM and entry routing
72: → Director approves package and releases Engineering
73: → Engineer builds, verifies and fills factual handoff
74: → Director commits/pushes the numbered engineering candidate
75: → QA branch starts at that exact candidate; Q1 recon and independent plan
76: → QA Lead approves; Director releases Q2 execution
77: → Authorized repair/retest on the same QA branch as needed
78: → QA Lead product verdict; required cleanup and acceptance
79: → Architect closeout; bounded Engineering closeout; Director final Git actions
80: → Review checkpoint 1: after FFM build and its independent QA finish.
81: → Disposition findings; RRM only for approved findings requiring repairs; a clean review requires no RRM.
82: → Continue Engine 1 phases/modules and QA; Engine 2 review only after all are closed.
83: → Review, module QA, cleanup acceptance, Gate D and Director release retain separate responsibilities.
84: ```

252: ## 3. FFM Anatomy — The Folder Structure
253: 
254: Every newly authored module includes a complete, module-specific `QAM/` prepared by the Architect from `03_BUILD_METHODOLOGY/_templates/QAM/`. QA Lead owns the reusable playbook and standing requirements. Engineer fills factual engineering records and handoff; QA Executor performs independent Q1 recon and test planning; QA Lead approves the plan; Director releases execution; QA Executor performs Q2 and authorized retest; QA Lead adjudicates and certifies. `QAM_PLAYBOOK.md` owns this packaging and sequence. Existing modules already in flight retain their recorded sequence until an attributable amendment.
255: 
256: The FFM lives under the project’s `agent_docs/` module convention. Its `QAM/` records and support material are excluded from production inputs and artifacts, with verification under `DEPLOYMENT_PLAYBOOK.md`.
257: 
258: Every FFM follows the same folder structure. Names and content vary per project; structure does not.

341: 
342: The structure encodes three principles:
343: 
344: 1. **Discoverability** — an AI tool opening the FFM finds the entry point (`CLAUDE.md` at root) and follows the navigation chain. No hunting.
345: 
346: 2. **Separation of concerns** — project-specific content is isolated in underscore-prefixed folders so it can be replaced wholesale without touching the reusable parts.
347: 
348: 3. **Compounding leverage** — the reusable parts (skill, playbook, verification) get refined with every run. By Run 4 or 5, the playbook is tight enough for autonomous overnight runs.

570: 
571: - **APP_BRIEF.md FIRST** — scope must be locked before contracts or screens can be specified

724: ## 22. Field Case Studies (the validation record)
725: 
726: **FIX-001 (ADK-HARNESS, legacy) — the pointer that lost the argument.** Symptom: chat history evaporated on reload. Mechanism chain: persisted session pointer restored correctly, then a mount-effect merge let a *mocked* service's seeded fake ids overwrite it ("fetched wins" applied to fiction). Lessons banked: the Engineer's CRITICAL-FINDING behavior (persistence alone was inert without the merge fix — surfaced, not silently handled) is the model for plan-stage honesty; merge precedence against mocked sources must favor persisted truth, with a comment scheduling re-evaluation when the source goes real; final disposition used **BLOCKED-UPSTREAM** honestly when the residual failure proved to live beyond the module's boundary — a FIX may PASS on its own contract while the symptom's remainder transfers to another module's gate (it did: the upstream history defect was confirmed and cured by the next BIM, post-mortem).
727: 
728: **FIX-002 (ADK-HARNESS, legacy) — the QA-born triple.** Three adjudicated findings, one surface region, one module, per-finding gates; chatService deliberately unfrozen for exactly one string (scope stated, not smuggled). QA verdict PASS-WITH-FOLLOW-UP-FINDINGS produced four new findings — the lifecycle compounding exactly as designed.

Fix: mode-namespaced keys + one-time legacy adoption (migration kindness). F06 (hydration flash) rode along with a store-level hydration gate. 22: ## 3. FEAT-Specific Doctrine
23: 
24: ### 3.1 Launch conditions are first-class
25: Features ride on top of moving systems. Every FEAT manager declares its launch condition in the status line AND in the Operator launch line itself (field pattern: *"Operator launch line (ONLY after BIM-002 closes)"*) — so even if future-you forgets, the manager remembers. Features never share a lane with a risky module: the riskiest module of a campaign carries zero passengers.
26: 
27: ### 3.2 Version doctrine: v1 now, v2 seeded, NOT built
28: Ship the simplest capable version using what the platform already provides (field example: browser-native speech before premium TTS). The upgrade path is designed in — the capability isolated behind ONE swap point (a utility, a service function) — and the v2 design lives as a **seed note in the retrospective**, not as built code, not as new dependencies, not as env vars. Garnish (LLM-generated titles, premium voices, optimistic locking) is named as garnish and deferred out loud.
29: 
30: ### 3.3 Scope discipline against feature gravity
31: Features attract siblings ("while we're adding copy, let's also…"). The manager's OUT-of-scope section says it loud, including: adjacent icons that stay decorative, input modalities not in scope (voice OUT ≠ dictation IN), and restyling beyond wiring what exists. QA-finding-born features cite their finding IDs and carry ONLY the adjudicated findings — rejected findings never smuggle in.
32: 
33: ### 3.4 Mode parity — where both modes support the feature
34: When the application's modes (e.g., mock and live) both support a feature's surface, the feature must behave consistently in both — proven by a gate, not assumed. Some features are legitimately mode-specific; the manager declares mode scope explicitly. A feature that *secretly* depends on a live backend while claiming mode-agnosticism is a misclassified BIM.
35: 
36: ### 3.5 Accessibility is not a garnish
37: When a feature IS the accessibility path (audio-first operators, keyboard paths), it carries normal-priority scheduling and its gates test the accessible experience itself (field gate: *"if it reads markdown symbols aloud, it fails"*).
