31: ## 1. Philosophy and Factory Seats
32: 
33: Resolve authority by the question being answered: disk and recon establish what exists; approved artifacts establish what is authorized; the named domain owner defines the reusable pattern. A conflict between these is not permission to substitute one for another. Stop the affected work, record both sources and their revisions, and obtain the Director’s attributable ruling. Preserve stage-specific authority within its stated scope.
34: 
35: ### Shared terminology
36: 
37: A seat defines responsibility; a persona or model name does not grant permission. Director is the human scope, access and release authority; Operator and Coordinator are contextual names for that human responsibility. Architect owns assembly and scope interpretation; Engineer owns implementation and factual handoff; QA Lead owns QA doctrine, plan approval, adjudication and certification; QA Executor independently plans and tests. Designer and deployment responsibilities remain distinct. “Architect” does not name the human approver in an authority rule.
38: 
39: Keep lifecycle axes separate: Blueprint phases describe the Factory pipeline; SFP implementation phases describe build disciplines; FFM sub-phases and Frontend Build Phase stages describe execution within a module; roadmap phases describe product scope. Record each stage’s parent, entry artifacts, exit evidence and approver in the module contract. Demo deployment is not Gate Q or Gate D. Engine 1 is module engineering and module QA. Engine 2 is independent system review after all Engine 1 phases and their QA are closed. The separate post-FFM review occurs after FFM and its QA. Only dispositioned findings requiring repair produce RRM work.
40: 
41: Schema-first, approved specifications, incremental verification and recorded changes remain required.

189: ## 2.5 Module Identity & QA Handoff  *(Factory-wide — governs BIM, FIX, FEAT, and all future module types)*
...
192: 
193: **Canonical ID format: `<TYPE>-<NNN>-<APP-SLUG>`** — e.g., `BIM-006-ADK-HARNESS`, `FIX-004-CYBER-PHARMA`, `FEAT-002-ADK-HARNESS`.
194: 
195: 1. The slug comes from the application's canonical identity in its project brief / APP_BRIEF. *(A central `APP_REGISTRY.md` is a proposed future addition, pending separate Operator approval; until it exists, no document may cite it as a source of truth.)*
196: 2. The ID appears on: the module folder name, every document header inside it, the `ACCEPTANCE_SPEC.md`, QA references, retrospectives, changelog entries, and cross-document links.
197: 3. Casing: canonical ID UPPERCASE in documents and folder names; git branches lowercase-kebab; commit tags carry the canonical ID.
198: 4. Rationale (stated, not assumed): module artifacts escape their folders — into QA reports, branches, search results, and handoffs. A naked `FIX-002` becomes ambiguous the day a second application mints one. Provenance travels with the artifact.
199: 5. Legacy: modules created before this doctrine keep their unsuffixed names as LEGACY IDs — no retroactive mass-renaming. New citations append the app parenthetically: "FIX-002 (ADK-HARNESS, legacy)."
200: 
201: ### QA Handoff — the `ACCEPTANCE_SPEC.md` Contract
...
204: 2. **Ownership:** acceptance criteria are **seeded from the approved module contract — Architect/Operator-defined — before implementation.** The Engineer maintains the spec in sync with approved scope and finalizes it at handoff, but may not silently add, remove, weaken, or redefine a requirement; scope changes require approval.
205: 3. **Numbering:** acceptance requirements use **`AC1, AC2, …`** — a Factory decision effective 2026-08-10. Module-internal engineering gates keep their own ID families (`X*`, `V*`, `N*`, `P-G*` …); a gates↔AC mapping table in the spec is encouraged. Bare `A*` is reserved for recon assumption checklists. Legacy specs using gate IDs stand as legacy.
206: 4. **Minimum contents:** canonical module ID + owning app · objective · in-scope / explicit out-of-scope · numbered ACs, testable and observable · expected behavior per AC incl. error surfaces · **environment/setup prerequisites and every manual Operator step, called out FIRST** · regression expectations · manual-only points · known limitations · follow-up work outside this contract.
207: 5. **Authority chain:** QA owns the verdict — Factory vocabulary exactly: **PASS / PASS WITH FOLLOW-UP FINDINGS / PASS WITH KNOWN RISK / FAIL / BLOCKED.** The **Operator holds final adjudication and release authority.** The Architect advises on architectural classification and routing. An in-scope acceptance failure needs no one's permission to be a FAIL. Accepted findings reach Engineering only as approved module content.
208: 6. **Gate Q is mandatory for all code-bearing modules.** Only documentation-only / non-runtime changes may receive a recorded Operator QA waiver.
209: 
210: Every newly authored module includes a complete, module-specific `QAM/` prepared by the Architect from `03_BUILD_METHODOLOGY/_templates/QAM/`. QA Lead owns the reusable playbook and standing requirements. Engineer fills factual engineering records and handoff; QA Executor performs independent Q1 recon and test planning; QA Lead approves the plan; Director releases execution; QA Executor performs Q2 and authorized retest; QA Lead adjudicates and certifies. `QAM_PLAYBOOK.md` owns this packaging and sequence. Existing modules already in flight retain their recorded sequence until an attributable amendment.
211: 
212: The Director commits and pushes the completed engineering candidate on the numbered product branch, then creates `qa/<module-branch>` at that exact commit. Engineer performs approved repairs and QA Executor independently tests on that same QA branch, with separate writable lanes and one active writer during repair or measurement. The QA branch continues to final integration; do not transfer work back or abandon it as the normal workflow. After the QA Lead’s verdict and required cleanup, the Architect issues closeout instructions, Engineer performs bounded closeout, and the Director performs final commits, merge and push. Preserve product, execution, evidence and closeout identities separately.

428: 
429: ### Service Function Template
430: 
431: **Executable error-handling example withdrawn.** Return a generic client error. Log only an allow-listed structured record: correlation ID, operation, normalized failure class and safe provider code. Exclude raw exceptions, request bodies, credentials, payment details and personal data. A negative test plants synthetic sensitive markers and asserts that neither client output nor retained logs contain them. The Architect includes the API trust-boundary matrix in the acceptance contract; the Engineer supplies engineering results, the QA Executor derives independent checks, and the QA Lead approves and grades them. Cover unauthenticated/wrong-role/wrong-owner calls, forged payment status, tampered totals, duplicate and concurrent requests, invalid signatures, pre-acceptance persistence failure, post-acceptance worker failure, and stale/out-of-order events. Each case records status, absence of unauthorized effects, persisted final state and retry/recovery evidence. TESTING_PLAYBOOK owns the matrix; commerce, subscription and API manuals refer to it. Declare wire and internal types separately and normalize once at the service boundary. A named operation uses one parameter signature and typed result envelope in its service, route and client examples. Any independent alternative is explicitly labeled with its own contract; callers do not silently mix array, paginated and wrapped results. Implement only against a verified project service contract; distinguish empty success from failure and redact internal/upstream detail from public responses and logs.

104: ### The Locked Rules (Lesson L1 — paid for in the field)
105: 
106: 1. **Just-in-time authoring.** Implementation-grade module docs are authored only after (a) the previous module's retrospective exists and (b) a fresh recon of the current repo state is in hand. Before that, a phase holds only a **Phase Seed Brief** (mission, why, dependencies, likely scope, open questions), explicitly non-executable.
107: 2. **Contracts freeze at handoff.** Requirements and acceptance criteria remain immutable except through an attributable approved amendment. Declared lanes inside the module remain writable by their assigned owners for engineering handoff, recon, plans, evidence, findings and rulings. QA records live in the module’s `QAM/` under `agent_docs/`. A test-plan edit cannot amend acceptance criteria.
108: 3. **DRAFT until stamped.** Docs coexisting with a not-yet-run recon carry DRAFT — CLAIM STATUS until the post-recon verdict stamps them FINAL. After the stamp, requirements and acceptance criteria are frozen; changes require an attributable approved amendment. Declared engineering handoff and QA evidence lanes remain writable by their assigned owners.
109: 4. **Placeholders from the first keystroke.** Real URLs, credentials, and infrastructure values NEVER enter documents — even as examples. Structural placeholders only; real values live in local env files, supplied by the Coordinator in-session.
110: 5. **Lessons live at repo level** (`agent_docs/LESSONS/`, timestamped, one lesson per file, append-never-edit) — modules end; lessons compound.

114: ## 7. Standing Engineer Doctrine (bake into every manager)
115: 
116: - **Git/cloud authority:** read-only Git inspection is allowed; the Director performs all Git mutations. The BIM Engineer does not deploy and supplies exact file lists and suggested commit messages.
117: - **Do not silently deviate:** a change outside the authorized writable surface, including diagnostic, test-runner or build configuration changes, requires explicit authorization before execution. Report the proposed change and its evidence; later ratification is not prior authorization.
118: - **Baseline-first regression:** full suite before the first change (entering red? repair-or-report before proceeding — a red baseline is a finding, possibly a prior module's defect), full board after the last. Pre-existing failures are proven pre-existing, never silently repaired or suppressed.
119: - **Failure policy is declared per module contract — degrade is not a universal law.** Degrade-with-console-error-and-safe-fallback applies only where the module contract explicitly declares that losing the dependency is safe (e.g., a convenience index, a receipt). Security, audit, financial, tenant-isolation, and data-integrity-critical dependencies may require **fail-closed** behavior — the contract says which, per dependency, before the Engineer builds.
120: - **Stop means stop.** Momentum after a stage gate is the enemy; the next stage begins only on the Coordinator's plain words.

141: ## 9. QA Engagement (the Red Team seat)
142: 
143: Every newly authored module includes a complete, module-specific `QAM/` prepared by the Architect from `03_BUILD_METHODOLOGY/_templates/QAM/`. QA Lead owns the reusable playbook and standing requirements. Engineer fills factual engineering records and handoff; QA Executor performs independent Q1 recon and test planning; QA Lead approves the plan; Director releases execution; QA Executor performs Q2 and authorized retest; QA Lead adjudicates and certifies. `QAM_PLAYBOOK.md` owns this packaging and sequence. Existing modules already in flight retain their recorded sequence until an attributable amendment.
144: 
145: The Director commits and pushes the completed engineering candidate on the numbered product branch, then creates `qa/<module-branch>` at that exact commit. Engineer performs approved repairs and QA Executor independently tests on that same QA branch, with separate writable lanes and one active writer during repair or measurement. The QA branch continues to final integration; do not transfer work back or abandon it as the normal workflow. After the QA Lead’s verdict and required cleanup, the Architect issues closeout instructions, Engineer performs bounded closeout, and the Director performs final commits, merge and push. Preserve product, execution, evidence and closeout identities separately.
146: 
147: Required cleanup removes only authorized disposable execution debris, temporary credentials/authentication state, and owned QA processes or browser contexts. Retain durable evidence, required failed attempts and justified helpers. QA Lead governs retention and cleanup acceptance; certification, Architect closeout and Director release remain separate responsibilities. Record command, working directory, exit code and unfiltered safe output, with sensitive data excluded at collection. Prove product, tests, configuration and contract identity unchanged by cleanup. Module QA records live under `agent_docs/` in their module `QAM/`; verify production exclusion under `DEPLOYMENT_PLAYBOOK.md`.
148: 
149: - QA receives the spec and authors its own attack: `QA_PLAN.md`, manual sequences, exploratory probes, state-transition and negative-path testing. The most valuable field finding of the pilot campaign came from deliberately breaking state, not from following the happy path.
150: - QA findings carry a **QA-owned verdict**; the **Operator holds final adjudication and release authority** when a product/scope/risk decision is required; the **Architect advises** where architectural classification or routing is needed. An in-scope acceptance failure does not need anyone's permission to be a FAIL. Accepted work routes to Engineering only as approved module content — rejected findings never land on the Engineer's desk.
151: - QA independently tests the declared engineering candidate after handoff. Requirements and acceptance criteria remain frozen; QA recon, plans, evidence, findings and rulings remain writable in their declared lanes. QA cannot amend acceptance by changing a test plan.
152: - Evidence bar is symmetric: QA claims cite file:line, payloads, or reproducible steps; findings without evidence are returned unread.
153: - Verdict vocabulary — exactly the Factory QA set, no local dialects: **PASS / PASS WITH FOLLOW-UP FINDINGS / PASS WITH KNOWN RISK / FAIL / BLOCKED.** Findings are severity-classified, each explicitly marked blocking-or-not for the module under test.

155: ## 10. Contracts & Seams
156: 
157: - Route-handler/API **external contracts freeze** across module boundaries; only internals are ported (field proof: a middleware was replaced under an unchanged seam with zero frontend diff — the entire point of designing the seam one module earlier).
158: - Contract changes ship as **numbered amendments** (A1, A2 …) that supersede specific sections and inherit the rest, keeping history honest.
159: - When replacing a system, **the old system is the oracle for its replacement**: equivalence gates + fixture batteries encode its observable behavior; the old system stays deployed and untouched until a Coordinator retirement ceremony AFTER all gates pass.
160: - Kill switches are designed in: env-flag fallbacks (mock mode), git-revert paths, and the not-yet-retired predecessor. A kill switch that has never been flipped is a prayer — test the flip as a gate.

162: ## 11. Anti-Patterns (block these)
163: 
164: - **Pre-authoring against assumptions** — implementation docs written before recon (L1's origin: two defects authored into a module six days before evidence existed)
165: - **Mid-mandate contract mutation** — changing frozen requirements or acceptance criteria without an attributable approved amendment; declared owner-specific output lanes remain writable
166: - **Scope smuggling** — "while I'm here" fixes, passengers on risky modules; one variable per experiment
167: - **The Engineer grading his own paper** — acceptance spec drifting into a QA plan, or QA skipped because the board is green
168: - **Momentum through a stage gate** — starting the next stage in the same session/on the same nod
169: - **Real values as examples** — a URL in a doc's example row is a URL in git history forever
170: - **Naked module IDs in new work** — provenance is doctrine now
171: - **Happy-path-only QA** — if nobody deliberately stressed the product, it wasn't QA
