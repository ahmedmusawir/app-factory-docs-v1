# STANDING_INVARIANTS.md — The Ten Acceptance Families and Their Checks (D19 / D20)

> Shared reference. **Sol** derives `DOCSET_SYNC_ACCEPTANCE_SPEC.md` from these families plus the approved IDs and map rows — and from nothing else (derivation-only rule). **Cody** verifies each AC with the check named here at `QA_START_SHA` / `QA_RETEST_SHA`. **Claudy** runs the mechanical checks himself on the TINY path (under the recorded QA waiver) and presents the output at Gate 4. These families are the ONLY standing source an AC may cite besides an approved Correction / Intake ID or an approved UPDATE MAP row. Adding a family is a skill-evolution change, not a run decision.

Notation: `<base>` = the run's base SHA (main at branch creation); `<cand>` = the SHA under test; `<run>` = the durable folder `_AUDIT/SYNC_<date>_<slug>/`. Commands are illustrative shapes; the QA seat pastes the actual command and output as EVIDENCE.

## Preconditions (not ACs — a failed precondition is BLOCKED, not FAIL)

- `CONTENT_SHA` is recorded in `SYNC_HANDOFF.md`, exists on `origin/<branch>`, and is an ancestor of `QA_START_SHA` (`git merge-base --is-ancestor CONTENT_SHA QA_START_SHA`).
- `QA_START_SHA` equals `git rev-parse origin/<branch>` at the moment Cody starts (and `QA_RETEST_SHA` likewise per cycle). A moved tip invalidates prior PASS rows (D15a).
- The approved map (§O APPROVED) and the approved spec (Gate 3) are present in `<run>/` at `<cand>`.
- The lint runner executes on the QA rig.

## The derivation-only rule, restated for Sol

An AC is lawful only if its **Derived-from** field names (a) a Correction ID's invariant or preservation line, (b) an Intake ID's approved disposition, (c) an UPDATE MAP row (§C row number, §F row, §H row, §J row …), or (d) one of the ten families above. Sol may split a family into several ACs, merge related IDs into one AC, and phrase them testably. Sol may NOT add a requirement that has no such source — that would make QA an author of doctrine (D20, D17).
