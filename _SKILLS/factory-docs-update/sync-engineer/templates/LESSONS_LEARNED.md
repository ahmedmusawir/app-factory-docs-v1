# LESSONS_LEARNED.md — <PROJECT NAME>

> Project-side lessons bin. This file is what the `factory-docs-update` family's Engineer seat looks for at intake (Phase 1). Lessons live HERE until a retrospective flags them for doctrine; they reach the Doctrine Hub only via that skill's process — never by hand-copying.
> Convention: structural lessons (change how the factory works) get flagged for doctrine; project-local lessons (specific to this app) stay here permanently as project memory.
> A retro may export flagged lessons as a DOCTRINE_PROMOTION pack. Drop the pack — or this file — into the Hub clone's `_INBOX/` (the standing cargo bay); the skill classifies it as a DOCTRINE JOURNAL / LESSON and assigns each entry an intake ID (`IN-<run>-<NN>`).

---

## Format — one entry per lesson

### L-<NN> — <one-line title>
- **Date:** YYYY-MM-DD
- **What happened:** 2–4 sentences. The incident or discovery, concretely.
- **Evidence:** file paths, line numbers, PR/commit links, error text. (No evidence = not a lesson yet.)
- **The lesson:** the rule or correction, stated so a non-technical stakeholder gets it in one sentence.
- **Scope:** `PROJECT-LOCAL` | `DOCTRINE-CANDIDATE`
- **Doctrine target (if candidate):** which doc(s) and section(s) you believe should change — best guess is fine; the propagation analysis confirms or corrects it.
- **Status:** `OPEN` → `FLAGGED` (retrospective approved it for doctrine) → one of `ENCODED (PR #<n>, <intake ID>)` | `NO-CHANGE (approved Gate 2, <date>)` | `SPLIT (→ <target>, <XB ID>)` | `DEFERRED (Operator, <date>)` | `DECLINED (<reason>)`
